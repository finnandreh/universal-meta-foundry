# Universal Meta-Foundry v2
## A domain-agnostic operating system for deriving philosophy, meta-skill, framework, scaffold, prompts, and project generation rules for any future domain

---

# 1. Purpose

This document defines a **Universal Meta-Foundry v2**.

It is not a project plan for one domain.

It is the reusable system that exists **before domain selection**.

Its purpose is to allow a human to provide any future domain, project type, or engineering subject and then derive, in a controlled way:

1. domain philosophy  
2. domain meta-skill  
3. domain framework  
4. domain scaffold  
5. project structure  
6. prompt package  
7. Copilot operating instructions  
8. generation governance  

The Foundry is therefore a **pre-domain system**.

It creates the rules by which later systems are created.

---

# 2. Core Idea

Most AI-assisted work starts too low in the stack.

It starts with:
- code
- snippets
- direct prompting
- ad-hoc generation

That produces drift, inconsistency, and weak reuse.

The Foundry reverses the process.

It starts with:

- philosophy
- principle formation
- principle prioritization
- conflict resolution
- system decomposition
- framework formation
- scaffold formation
- generation rules
- execution governance

Only after those layers exist should code generation begin.

---

# 3. Foundry Formula

The complete model is:

```text
Subject
→ Subject Profiling
→ Principle Formation
→ Principle Prioritization
→ Principle Conflict Rules
→ Meta-Skill Derivation
→ Framework Formation
→ Scaffold Formation
→ Prompt Construction
→ Project Generation
→ Review / Hardening / Expansion
````

The operating formula is:

```text
Foundry = Philosophy + Meta-Skill + Meta-Framework + Meta-Scaffold + Domain Model + Governance + Generation Rules
```

# 5. Foundry Philosophy

## 5.1 Governing Principle

A system must be designed before it is implemented.

## 5.2 Core Principles

### 1. Structure before implementation

No project begins with code when architecture is still undefined.

### 2. Stable abstractions before variable implementations

Separate the long-lived conceptual structure from replaceable technical details.

### 3. Modules before functions

Think in responsibilities and boundaries before internal behavior.

### 4. Interfaces before integration

Communication contracts should be defined before cross-module coupling grows.

### 5. Diagnostics are mandatory

Every serious system must be observable.

### 6. Validation is part of design

Testing, verification, and simulation are design artifacts, not afterthoughts.

### 7. Generation must be governed

AI may generate implementation, but generation must occur inside explicit rules.

### 8. Reuse must be intentional

A framework is not reusable merely because it is generic. Reuse must be designed.

### 9. Human direction remains authoritative

The human defines purpose, approval, tradeoffs, and final decisions.

### 10. Systems must remain explainable

A generated structure that cannot be reasoned about is not a sound architecture.

---

# 6. Principle Prioritization

When principles conflict, the Foundry resolves them using this default order:

1. safety / correctness
2. clarity / explainability
3. architecture integrity
4. maintainability
5. validation capability
6. reusability
7. implementation speed
8. convenience

This means a faster implementation must not damage the architecture.

---

# 7. Principle Conflict Resolution Rules

When two principles push in opposite directions, resolve by asking:

1. Which option protects long-term architecture better?
2. Which option reduces hidden complexity?
3. Which option improves diagnosability?
4. Which option preserves future reuse?
5. Which option remains easiest to explain and validate?

If still unresolved:

* prefer the more modular option
* prefer the more observable option
* prefer the one that reduces implicit coupling

# 11. Foundry Modification — Minimal First-Step Prototyping and Structured Growth Policy

## 11.1 Purpose

This modification adjusts the Universal Meta-Foundry so that new domains do not begin with excessive scaffolding.

Instead, the Foundry must support a **minimal-first startup path** whose first goal is to get a **visual prototype** running as early as possible.

This visual prototype is used to:

* shape the frontend
* clarify the user-facing structure
* reveal missing concepts early
* make the domain easier to reason about before deeper generation begins

The system must therefore support two speeds:

1. **minimal prototype mode** for early shaping
2. **full structured generation mode** for later expansion

---

## 11.2 Core Rule

When a completely new domain starts, the Foundry should **not immediately generate maximum scaffold depth**.

Instead, it should first generate only the minimum required structure needed to:

* define the domain direction
* create a visual prototype
* shape the frontend
* allow fast correction before deeper generation
* keep the architecture open while the domain is still being discovered

This prevents early over-commitment to structures that may later need to change.

---

## 11.3 Minimal-First Startup Policy

For a new domain, the default startup behavior should be:

### Step 1 — create the minimum domain shell

Only the minimum initial structure should be created.

This should normally include:

* domain name
* short domain description
* early goals
* prototype notes
* minimal task set
* minimal frontend idea
* minimal project metadata

### Step 2 — create a visual prototype first

Before full domain scaffolding begins, the Foundry should allow creation of:

* a simple frontend shell
* a visual layout
* a rough control interface
* early navigation structure
* prototype interaction points

This prototype does not need full backend completeness.

Its role is to help define:

* what the system should look like
* what user interaction exists
* what main data blocks are needed
* what later modules are likely to be required

### Step 3 — refine the domain through the prototype

Once the visual prototype exists, the user can refine:

* terminology
* workflows
* modules
* entities
* data structures
* project boundaries
* reuse opportunities

Only after this should the Foundry begin deeper scaffold generation.

---

## 11.4 Controlled Scaffold Growth Rule

The Foundry must grow scaffolding in layers.

It must not assume that every new domain is ready for full deep generation at the beginning.

Instead, scaffold depth should increase progressively:

```text
Visual Prototype
→ Minimal Domain Shell
→ Core Structure
→ Domain Framework
→ Full Scaffold
→ Implementation Layers
```

This means the system should be allowed to remain intentionally light in the beginning.

---

## 11.5 Frontend-First Discovery Rule

For many domains, especially new ones, the frontend or visible interaction model helps define the real structure faster than backend-first generation.

Therefore the Foundry should support:

* frontend-first prototyping
* visual exploration before deep architecture lock-in
* editable GUI-driven domain shaping
* early interface definition before implementation depth expands

The prototype is not separate from the architecture.

It is an early discovery instrument.

---

## 11.6 Structured Growth Requirement

Even though startup should be minimal, the Foundry must still support **very detailed structured expansion** once the system begins to grow.

As new systems are built, the folder system must become highly structured and descriptive.

The hierarchy should support all major identity levels, such as:

* domain
* output
* client
* project
* system
* module
* model
* implementation
* documentation
* generated artifacts

The folder structure should be able to express these levels clearly and in a reusable way.

---

**folder structure must be explicit, layered, reusable, and descriptive at every level.**

---

## 11.8 Internal Client Rule

One client must always exist from the beginning:

```text
internal
```

The `internal` client is always built first.

Its purpose is to serve as:

* the Foundry’s own development space
* the place where reusable models are first created
* the location for common parts
* the home of generic structures that may later be reused in real client systems
* the staging area for prototype concepts before external client assignment

The `internal` client is therefore not optional.

It is the default seed environment.

---

## 11.9 Reuse Model Policy

Inside the `internal` client, the Foundry should support creation of reusable assets such as:

* models
* reusable parts
* interface definitions
* shared entities
* common workflows
* scaffold fragments
* prototype patterns
* documentation fragments

This allows future domains and client projects to reuse parts instead of recreating them.

The system should always favor:

* reusable descriptions
* reusable structures
* reusable models
* reusable parts

when reuse improves clarity and consistency.

---

## 11.10 GUI Information Capture Rule

The GUI should be capable of holding or generating all necessary detailed information needed for later structured growth.

This includes, where relevant:

* domain information
* client selection
* project identity
* system identity
* module grouping
* task descriptions
* state handling
* prototype notes
* reuse markers
* dependencies
* ongoing work context

Some of this may be explicitly entered in the GUI.
Some of it may be generated from Foundry logic.

The GUI should therefore be treated as both:

* a control surface
* a structured metadata editor

---

## 11.11 Task State Modification Rule

The Foundry should treat task states differently depending on intent.

### `todo`

Tasks in `todo` are eligible for active generation decisions.

These are the tasks we may ask Copilot to create now, depending on the current generation step.

### `planned`

Tasks in `planned` must normally be held back.

These represent work that is recognized but intentionally not generated yet.

Planned tasks should remain visible for structure and future direction, but should not automatically enter implementation generation.

### `done`

Tasks in `done` are completed reference items and should normally be excluded from generation, unless explicitly included for documentation or review purposes.

---

## 11.12 Ongoing Systems Context Rule

If a system is already ongoing, the Foundry should preserve at least a small amount of structured context about it.

This context can include:

* current purpose
* current phase
* short status description
* active modules
* known blockers
* recent decisions
* next intended actions

This information does not need to be overly large, but it should exist so the system is not treated as contextless every time generation resumes.

This helps:

* continuity
* reuse
* better prompt generation
* reduced drift between sessions

---

## 11.13 Practical Operating Rule

The Foundry should therefore operate like this for new domains:

### At the beginning

* stay light
* define only what is needed
* get a visual prototype running
* use the prototype to discover the domain
* avoid over-scaffolding

### As clarity increases

* expand folder structure
* expand documentation
* expand models
* expand modules
* expand task depth
* enable richer generation packages

### As systems mature

* enforce strong hierarchy
* separate clients, projects, systems, outputs, and reusable models
* preserve structured metadata
* maximize reuse from the internal client and shared models

---

## 11.14 Meta Prompt Adjustment

When activating the Foundry for a new domain, apply this additional rule:

> Do not begin by over-scaffolding the domain.
> Start with the minimum structure required to create a visual prototype and define the frontend shape.
> Use that prototype to refine the domain before generating the deeper framework and scaffold.
> As the system grows, expand into a highly structured folder hierarchy that clearly separates internal reuse, clients, projects, systems, outputs, and reusable models.
> Always build the `internal` client first as the seed environment for reusable models and common parts.
> Treat `todo` as generation candidates, `planned` as held future work, and preserve a small structured context for ongoing systems.

---

## 11.15 Engineering Summary

This modification changes the Foundry from:

```text
new domain
→ full scaffold immediately
```

to:

```text
new domain
→ minimal domain shell
→ visual prototype
→ frontend definition
→ domain refinement
→ controlled scaffold expansion
→ full structured system growth
```

This keeps early work fast and flexible while still preserving the long-term goal of deep, highly structured, reusable system generation.

# 25. Plan Agent

The Plan Agent is the planning controller that decides what to generate next and at what depth.

## 25.1 Purpose

The Plan Agent should:

* keep work aligned with Foundry philosophy
* select the next highest-value step
* enforce minimal-first startup for new domains
* prevent premature over-scaffolding
* stage structured expansion as clarity increases

## 25.2 Inputs

The Plan Agent reads:

* domain model JSON
* task states (`todo`, `planned`, `done`, and optional extended states)
* current system context for ongoing work
* generation options (docs, tests, simulation, diagnostics)
* project maturity level (prototype, core, framework, full scaffold, implementation)

## 25.3 Outputs

For each run, the Plan Agent should produce:

* current phase
* selected tasks for this cycle
* deferred tasks with reason
* target artifacts to generate
* acceptance checks for completion
* next-step recommendation

## 25.4 Planning Mode Selection

The agent must pick one mode before planning:

1. `prototype_mode`
2. `growth_mode`
3. `hardening_mode`

### `prototype_mode`

Use when the domain is new or unclear.

Plan should prioritize:

* minimal domain shell
* visual frontend prototype
* early navigation and interaction model
* terminology and workflow discovery

### `growth_mode`

Use when prototype clarity is sufficient.

Plan should prioritize:

* core structure expansion
* module and interface formalization
* scaffold layering
* docs/models/task depth growth

### `hardening_mode`

Use when major structure already exists.

Plan should prioritize:

* validation completeness
* diagnostics depth
* dependency cleanup
* naming and architecture consistency
* reproducibility of generation outputs

## 25.5 Task Selection Rules

The Plan Agent should select tasks in this order:

1. `todo` tasks required for current phase gates
2. `todo` tasks that unblock multiple downstream tasks
3. high-priority `todo` tasks with low coupling risk

The Plan Agent should not automatically pull `planned` tasks into active generation.

`planned` tasks may be promoted only when:

* current-phase gates are satisfied
* promotion reduces blockers or drift
* the promotion reason is explicitly recorded

`done` tasks are excluded from generation by default.

## 25.6 Phase Gates

Progression should follow explicit gates:

1. Prototype Gate: visual shell exists and interaction model is testable.
2. Core Gate: key modules and interfaces are named and bounded.
3. Framework Gate: architecture/docs/tasks/models are coherent.
4. Scaffold Gate: directory and artifact hierarchy are explicit.
5. Implementation Gate: active tasks can generate safely.
6. Hardening Gate: diagnostics/validation coverage is acceptable.

If a gate fails, the agent plans remediation tasks instead of advancing.

## 25.7 Planning Loop

The agent loop should be:

```text
Load Context
→ Determine Mode
→ Evaluate Current Gate
→ Select Candidate Tasks
→ Filter by State Policy
→ Emit Plan Packet
→ Execute Generation Cycle
→ Record Outcomes
→ Re-evaluate Gate
```

## 25.8 Plan Packet Schema

```json
{
  "phase": "prototype_mode",
  "current_gate": "Prototype Gate",
  "selected_tasks": ["task_001", "task_003"],
  "deferred_tasks": [
    {
      "id": "task_010",
      "reason": "state=planned"
    }
  ],
  "artifacts": [
    "web/index.html",
    "web/app.js",
    "docs/prototype_notes.md"
  ],
  "acceptance_checks": [
    "Prototype renders",
    "Core navigation path is clickable",
    "Domain terms updated in model"
  ],
  "next_recommendation": "Promote to growth_mode after prototype review"
}
```

## 25.9 Stop Conditions

The Plan Agent should pause and request human decision when:

* two gates conflict and no principle priority resolves it
* task promotions from `planned` would change scope significantly
* architecture integrity would be reduced by speed-driven shortcuts
* the domain objective is ambiguous or changed

In these cases, the agent should emit:

* decision needed
* impacted artifacts
* risk summary
* recommended options

### 26.33 Foundry Evolution Engine (Living System Policy)

Date: 2026-03-12

To give the Foundry "life" over time, add a persistent evolution loop that learns from usage and proposes safe improvements to GUI structure, setup catalogs, and prompt packet JSON.

Purpose:

* keep the system adaptable as client needs grow
* turn repeated manual edits into reusable patterns
* suggest high-value improvements without breaking stability

Core behavior:

1. Observe
  * capture recurring user actions and repeated manual work
  * detect frequent custom fields added for specific clients/projects
  * track where handoff readiness repeatedly fails

2. Learn
  * convert repeated patterns into candidate "Foundry enhancements"
  * classify candidates as:
    * GUI enhancement
    * JSON schema extension
    * setup catalog improvement
    * workflow/governance rule update

3. Propose
  * emit a human-readable "Suggested Modification" card in the GUI
  * include:
    * what problem is being solved
    * impacted GUI fields/panels
    * impacted JSON keys
    * migration/compatibility impact
    * confidence level

4. Gate
  * no automatic structural change without approval
  * require explicit user decision:
    * accept now
    * defer
    * reject
  * require schema version bump when JSON structure changes

5. Record
  * store accepted changes as evolution entries so future projects inherit improvements
  * preserve rejected/deferred proposals to avoid noisy repetition

Minimum JSON additions:

* `evolution.enabled` (boolean)
* `evolution.suggestions[]` (pending suggestions with rationale)
* `evolution.accepted[]` (approved upgrades with date/version)
* `evolution.rejected[]` (rejected upgrades with reason)
* `evolution.last_reviewed_at` (timestamp)

Suggested suggestion object shape:

```json
{
  "id": "sugg_20260312_001",
  "type": "json_schema_extension",
  "title": "Add client compliance profile",
  "reason": "Field manually added in 5 projects",
  "impact": {
    "gui": ["Domain Draft"],
    "json_keys": ["domain.compliance_profile"],
    "schema_version_change": true
  },
  "status": "pending",
  "confidence": "high"
}
```

GUI requirements for living evolution:

* add an `Evolution Inbox` panel for pending suggestions
* show impact badges: `GUI`, `JSON`, `Workflow`, `Low Risk`, `Needs Migration`
* one-click actions: `Accept`, `Defer`, `Reject`
* include a short plain-language summary for non-technical users

Safety and governance:

* accepted JSON-structure changes require:
  * schema version increment
  * backward import compatibility path
  * migration note in this master document
* changes affecting generation behavior require:
  * updated handoff checklist criteria
  * explicit note in Copilot instructions/prompt packet rules

Operating cycle:

```text
Observe Usage
→ Detect Pattern
→ Build Suggestion
→ Human Review
→ Accept/Defer/Reject
→ Apply + Version + Document
→ Re-evaluate on future usage
```

Foundry rule going forward:

* every significant recurring manual pattern should become either:
  * a reusable setup catalog option,
  * a new optional GUI field,
  * or a governed prompt packet/schema extension.
* this keeps the Foundry continuously improving while preserving architectural control.

### 26.35 Soul Brain Smart Capability Catalog

Date: 2026-03-12

To strengthen the Soul Brain system, define a capability catalog that can be enabled progressively by profile level.

Purpose:

* keep intelligence practical and modular
* avoid overloading early-stage Foundries
* make upgrades predictable and governed

Capability list:

1. Pattern Miner
  * detects repeated manual edits and recurring custom fields
  * proposes reusable catalog entries, optional GUI fields, or schema extensions

2. Drift Guard
  * checks alignment with core structure and principles
  * warns when domain/client/project/system context quality degrades

3. Reuse Recommender
  * suggests existing internal assets before creating new ones
  * prioritizes proven internal patterns for consistency and speed

4. Gate Predictor
  * estimates handoff readiness risk before formal review
  * highlights likely checklist failures early

5. Risk Radar
  * scores proposed changes by architecture impact, migration cost, and rollback complexity
  * surfaces risk tier as `low`, `medium`, or `high`

6. Schema Guardian
  * validates compatibility impact of new fields
  * proposes version and import-normalization requirements

7. Prompt Quality Critic
  * evaluates prompt packet clarity, completeness, and ambiguity
  * proposes concise improvements before handoff

8. Evolution Conflict Resolver
  * detects collisions between multiple accepted/pending suggestions
  * proposes option paths with tradeoff summaries

9. Plugin Fitness Advisor
  * for plugin Foundries, evaluates extension-point quality and compatibility stability
  * recommends metadata and migration hardening steps

10. Explainability Narrator
  * produces plain-language explanations for why each suggestion exists
  * keeps decision context understandable for non-technical users

11. Learning Budget Controller
  * limits number of suggestions per cycle to reduce noise
  * protects focus and trust in recommendation quality

12. Inheritance Auditor
  * verifies that child Foundries still honor parent principles and governance gates
  * reports divergence and remediation options

Profile mapping:

* `light` profile defaults:
  * Pattern Miner
  * Drift Guard
  * Learning Budget Controller
  * Explainability Narrator (summary mode)

* `standard` profile defaults:
  * all `light` capabilities
  * Reuse Recommender
  * Gate Predictor
  * Risk Radar
  * Prompt Quality Critic
  * Schema Guardian

* `extended` profile defaults:
  * all `standard` capabilities
  * Evolution Conflict Resolver
  * Plugin Fitness Advisor (when plugin mode is active)
  * Inheritance Auditor

Governance constraints:

* all capabilities operate under `suggest_only` unless explicitly overridden by policy
* structural/schema modifications still require approval gates
* high-risk recommendations require explicit risk note and rollback note in decision logs

JSON extension guidance (optional fields):

* `soul.capabilities.enabled[]`
* `soul.capabilities.disabled[]`
* `soul.learning_budget.max_suggestions_per_cycle`
* `soul.risk_threshold.auto_block_level`
* `soul.audit.last_inheritance_check`

Operational rollout rule:

1. start with `light` profile for new Foundries
2. promote to `standard` only after recurring complexity is observed
3. promote to `extended` only when cross-project scale or plugin complexity justifies it
4. record every profile change in this document and in Foundry JSON metadata

Outcome target:

* the Soul Brain remains useful, explainable, and lightweight at startup
* intelligence depth increases only when proven necessary
* every derived Foundry gets a consistent smart baseline without losing governance control
